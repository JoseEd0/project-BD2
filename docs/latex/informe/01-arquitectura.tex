\section{Diseño arquitectónico}

El sistema está organizado en capas (figura~\ref{fig:capas}). Cada capa usa solamente a las
que tiene debajo: el motor de consultas no conoce el API y el API no conoce la interfaz.
Las estructuras que evalúa el enunciado (páginas, árbol B+, hash extendible, algoritmos
externos, parser SQL y R-Tree) están implementadas en el proyecto. Las librerías externas
se usan solo para el servidor web (FastAPI), la interfaz (React y Leaflet), las gráficas y
las pruebas.

Hay cuatro decisiones de diseño que se aplican en todo el código:

\begin{itemize}[nosep, leftmargin=*]
  \item \emph{Acceso por páginas.} Todas las estructuras leen y escriben páginas de
        4\,096 bytes a través del mismo paginador. Todos los archivos abiertos comparten un
        solo buffer pool LRU de 2\,048 páginas (8~MiB). Ningún archivo se carga completo en
        memoria.
  \item \emph{Registros de tamaño fijo.} Así la posición de un registro dentro de su página
        se calcula directamente, y la capacidad de cada nodo sale de dividir el tamaño de
        la página entre el de una entrada.
  \item \emph{Código compartido.} La serialización de registros, el manejo de páginas y las
        métricas de distancia están cada una en un solo módulo, que usan tanto los índices
        como la búsqueda secuencial. Por eso una consulta devuelve lo mismo con índice o
        sin él.
  \item \emph{Parámetros configurables.} El tamaño de página, los umbrales y el número de
        particiones son campos de la clase \texttt{EngineConfig}. Las rutas y los puertos
        se leen de variables de entorno, y los parámetros de los experimentos se pasan por
        línea de comandos.
\end{itemize}

\paragraph{Ejecución de una consulta.} Una sentencia pasa por las etapas de la
figura~\ref{fig:etapas}: el lexer y el parser generan el AST, se validan nombres y tipos,
el planificador elige el camino de acceso y los operadores producen las filas. Junto con
el resultado se devuelve el plan de ejecución, y con \texttt{EXPLAIN ANALYZE} también las
filas y el tiempo de cada operador.

\paragraph{API e interfaz.} El API REST ejecuta sentencias SQL, lista las tablas, muestra
la estructura física de una tabla y de sus índices, y permite crear tablas a partir de un
archivo CSV. Cada pestaña del navegador tiene su propia sesión, lo que permite probar los
bloqueos con dos pestañas. La interfaz (figura~\ref{fig:interfaz}) tiene los cuatro paneles
que pide el enunciado (archivos, consultas, resultados y plan de ejecución) y, para la
Parte~2, un mapa que muestra el resultado, el centro y el radio de la consulta y los MBR
del R-Tree.
