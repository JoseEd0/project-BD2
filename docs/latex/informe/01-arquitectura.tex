\section{Diseño arquitectónico}

\subsection{El motor}

El motor está organizado en capas (figura~\ref{fig:capas}) y cada capa usa solamente a las
que tiene debajo: el motor de consultas no conoce el API y el API no conoce la interfaz.
Cada bloque es una carpeta de \texttt{src/}. Las librerías externas se usan solo para lo
que el enunciado no evalúa: el servidor web (FastAPI), la interfaz (React y Leaflet), la
extracción de características (OpenCV y librosa), las gráficas y las pruebas, además de
FAISS en la Parte~4.

Todas las estructuras leen y escriben páginas de 4\,096 bytes a través del mismo paginador,
con un solo buffer pool LRU de 2\,048 páginas (8~MiB); ningún archivo se carga completo en
memoria. Los registros son de tamaño fijo, salvo las columnas \texttt{TEXT}, que se guardan
fuera de la fila en un archivo de valores de longitud variable. La serialización, el
manejo de páginas y las métricas de distancia están cada una en un solo módulo que usan
tanto los índices como la búsqueda secuencial, por eso una consulta devuelve lo mismo con
índice o sin él. Los parámetros (tamaño de página, umbrales, $k_1$ y $b$ de BM25, $M$ de
HNSW) son campos de \texttt{EngineConfig}, y las rutas, claves y puertos se leen de
variables de entorno.

Una sentencia pasa por el lexer, el parser (que genera el AST), la validación de nombres y
tipos, el planificador, que elige el camino de acceso, y los operadores, que siguen el
modelo de iteradores (Volcano). Junto con las filas se devuelve el plan, y con
\texttt{EXPLAIN ANALYZE} también las filas y el tiempo de cada operador. La consola tiene
los cuatro paneles que pide el enunciado (archivos, consultas, resultados y plan), el mapa
de la Parte~2 y una página para cada búsqueda de las Partes~3 y~4, que muestran el SQL
exacto que se ejecuta.

\subsection{Las aplicaciones de la Parte 5}

Las cuatro aplicaciones del Anexo~A se hicieron como productos separados que usan el gestor
como se usaría una base de datos externa: solo por su API REST, con un cliente tipado
(\texttt{minigestor\_client}) y parámetros \texttt{\$n} en lugar de concatenar SQL. Una
prueba recorre \texttt{apps/} y falla si un servicio importa código del motor. La
figura~\ref{fig:servicios} muestra el despliegue con Docker Compose.

El gestor es el único contenedor con estado y no publica puertos: solo llegan a él la
consola y las API de las aplicaciones. Cada servicio tiene su propia clave con un rol: la
consola es \texttt{admin}, y cada API atiende con una clave \texttt{write} y usa una
\texttt{admin} solo para crear sus tablas al arrancar (\texttt{CREATE \ldots{} IF NOT
EXISTS}). Cada interfaz es un nginx que está solo en la red de su aplicación y reenvía
\texttt{/api} a su API, con límites de tamaño del cuerpo y de peticiones por segundo; así,
una interfaz no puede hablar con el gestor ni con otra aplicación. Las API no guardan
estado y escalan con réplicas detrás de su nginx; rostros usa además un Redis sin disco
para guardar los rastros de cada sesión en vivo. Cada aplicación tiene un trabajo de carga inicial (perfil
\texttt{seed}) que es repetible: una segunda ejecución no vuelve a cargar nada. Para
cargar sus datos usan una ruta de carga masiva en NDJSON que confirma lotes de 1\,000 filas
y construye los índices al final; con 10\,000 filas sin vector es 4.5 veces más rápida que
un \texttt{INSERT} por petición.
